# T02 verification — PostgreSQL ownership boundary

Date: 2026-09-23

## Implementation

- `backend/app/database/schema.sql` creates users, repositories, immutable
  repository snapshots keyed by repository and commit SHA, analyses, files,
  dependencies, and code issues. Composite foreign keys prevent child records
  from crossing repository or snapshot boundaries.
- `backend/app/database/__init__.py` provides initial schema creation and
  owner-scoped repository, snapshot, and analysis operations. Analysis writes
  require an existing snapshot with the exact repository ID and commit SHA.
- `backend/tests/database/test_store.py` exercises two users, the same URL,
  forbidden cross-owner reads/writes, SHA mismatch, and relational constraints.

## Test environment and commands

A temporary PostgreSQL **16.15** cluster was initialized in the task's
`work/postgres/data` directory with locale C and bound only to
`127.0.0.1:55432`. A disposable `t02_test` database was created. No
pre-existing database or service was used.

Before a PostgreSQL server was available:

```powershell
uv run pytest tests/database/test_store.py tests/contracts -q
```

Result: **12 passed, 3 skipped** at that point. The skips explicitly meant
the PostgreSQL integration behavior was unverified.

With `ARIADNE_TEST_DATABASE_URL=postgresql://t02@127.0.0.1:55432/t02_test`:

```powershell
uv run pytest tests/database tests/contracts -q
```

Result: **16 passed, 1 warning in 1.20s**. The warning comes from the
existing Starlette/TestClient `httpx` deprecation path. The four PostgreSQL
tests ran; none were skipped.

## Boundary and remaining scope

The store requires a trusted authenticated user ID on each operation. T02 does
not implement authentication, GitHub OAuth or permission checks, API routes,
token encryption, or a migration framework for future schema revisions.
Privileged direct SQL can bypass these application-level owner checks; API
integration must use the scoped store and a suitably restricted database role.
