# T20 — Repository chunk and Qdrant index

`chunk_snapshot(owner_id, snapshot, source_texts, repository_id=local_id)` requires the complete set of selected files from the pinned `RepositorySnapshot`. It verifies each UTF-8 text against the file's Git blob SHA and byte size, then emits deterministic overlapping line chunks. A chunk is at most 48 line segments and 8,000 characters by default; long single lines are split without discarding text. Each chunk carries owner, local repository ID, source GitHub repository ID, commit SHA, path, inclusive line range, ordinal, text and a content digest. Missing or extra files fail instead of producing a partial index. Repository text is data; this module does not import or execute it.

`index_snapshot(..., source_texts, document_texts=...)` accepts a separate optional mapping of raw UTF-8 document blobs selected by the GitHub ingestion service. The source mapping must still exactly cover `snapshot.included_files`; documents never change the code filter. Each document must be present in the same snapshot's file metadata and pass the same Git blob SHA and byte-size check as code. Eligible paths are root READMEs, text documents under `docs/` or `doc/`, and the named manifest/API/container documents allowed by ingestion. Hidden, generated, sensitive-name and `.env` paths are rejected; obvious private keys and credential values in document content fail indexing before any embedding call. The `kind` field distinguishes document chunks from code chunks; both retain owner, source and line provenance. README instructions remain untrusted text.

Private document input also requires `private_document_snapshot=PrivateRepositorySnapshot(...)` from the private GitHub reader. Its owner and complete repository snapshot must match the index call; the source GitHub ID and commit must match the current live scope. The wrapper alone grants no access: the trusted scope resolver still checks current permission before indexing and after embedding. Public scopes reject an injected private wrapper. The private reader must perform its own live token, allowlist and blob verification when fetching the document text; this index independently checks path and Git blob integrity again.

`QdrantIndex` requires a Qdrant client, a trusted `resolve_scope(authenticated_caller_id, local_repository_id)` callback and an injected embedding provider. The resolver must return `AuthorizedScope(owner_id, repository_id, source_repository_id, commit_sha, private)` only after checking local ownership **and live repository access**, including GitHub permission for private repositories. The local repository ID is the database UUID; the source repository ID is GitHub's ID from its snapshot. The callback must obtain the current commit SHA from trusted state. Caller input cannot supply a Qdrant filter or a search SHA. Indexing checks the source GitHub ID and SHA against that scope; search composes owner, local repository, source repository and current SHA filters internally. Scope is checked again after embedding and after search so a revoked private permission cannot yield results. `current_scope(caller_id, repository_id)` exposes the same live check to downstream answer generation. A denied or unavailable resolver fails closed.

The embedding provider contract exposes a stable `model_id`, positive `dimension`, `execution_location == "local"`, `embed_documents(texts)` and `embed_query(text)`. No default model or external API is configured. Missing providers and externally located providers fail explicitly. Production integration must supply a real local embedding model; synthetic vectors in tests verify storage and filtering mechanics only and make no semantic retrieval claim. The provider and resolver are trusted backend integrations, not request-body values.

One Qdrant collection is used per model ID and dimension, with cosine distance. The index validates existing collection dimensions, deterministic point IDs make reindex idempotent, and a scoped scroll removes points absent from the latest complete index, including old commit SHAs. All vectors are checked for exact size and finite numeric values before storage writes. Search returns source-linked hits for downstream RAG; answer generation and prompt construction are separate tasks.

Search asks Qdrant for a bounded 96–128 candidate pool **with the same owner, local repository, source repository and current SHA filter**. It checks every returned payload, then reranks by cosine score, terms actually present in the source/path, a small repository/project bilingual vocabulary, and penalties for many hits from one file or repeated picks from that file. Only a run of at least three standalone Markdown bullet questions is excluded from lexical evidence; code operators and FAQ lines containing an answer remain eligible. This counters long documents crowding out a distinct README or code file without a question-specific answer or a lower authorization threshold. `SearchHit.score` remains the original cosine score; result order reflects the rerank. Live scope is checked again after reranking, and path/line/SHA citation fields are unchanged.

Passing `document_texts=None` or an empty mapping on reindex removes previously indexed documents for that owner/repository/model. The ingestion service keeps its 64-file, 2 MB total and 512 KB per-file bounds; this module rechecks them. It does not accept redacted `.env` template text because that text no longer matches its original Git blob.

Run `uv run --directory backend pytest tests/rag/indexing -q` from the repository root. The tests use the real `qdrant-client` local mode for collection writes, filtered search and stale point deletion. They do not verify a remote Qdrant server, a production embedding model, or end-to-end API wiring. Concurrent index writes for the same owner/repository/model need serialization by the calling job layer; Qdrant writes here are not a transaction. The Qdrant service itself must be restricted to trusted backend access because its direct API can bypass application authorization.
