# Ariadne local HTTPS and GitHub OAuth setup

Ariadne uses one browser origin for the frontend, API and OAuth callback:

- Homepage: `https://localhost:8443/`
- GitHub OAuth callback: `https://localhost:8443/auth/github/callback`

GitHub's [OAuth app registration guide](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app) asks for a full Homepage URL and an Authorization callback URL. Its [authorization guide](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#redirect-urls) says the requested redirect must exactly match the registered callback when wildcard matching is disabled. Register the exact callback above with wildcard matching **off**. `localhost:8443` is the chosen local web origin; no public domain or paid hosting is required. GitHub's separate loopback-port exception is for native app redirects and is not needed here. The actual GitHub OAuth round trip remains unverified until an OAuth app is registered and its credentials are configured locally.

## Local preparation

**Windows file permissions are a prerequisite.** This checkout and its generated files must be owned by the current Windows user. The runnable repository, setup scripts, `.env.local`, and certificate files must have no allow rule for another user or group (except Windows `SYSTEM`); the `certs/` directory must also have inheritance disabled. `assert-local-acl.ps1` checks these rules without changing permissions. Certificate generation checks before writing private keys, and the HTTPS helper checks before reading `.env.local` or starting the server. If a check fails, setup stops. A separate trusted Windows administration step must establish a protected execution location and permissions; these scripts do not change the repository, parent directory, OS policy, or certificate trust store. Merely moving secrets to `%LOCALAPPDATA%` is insufficient when that directory grants another group read access. If another local account could already read the old files, restricting future access does not undo that exposure: assess rotation of the Fernet key, OAuth Client Secret, and local CA/server keys after protecting the location. Existing secret files are never overwritten automatically.

The code that performs these checks must itself run from a protected location. When other local accounts can modify the checkout, they can change a later startup script before the check runs; passing a check in this mutable checkout is not a complete isolation guarantee. This local setup remains blocked until that execution boundary and secret file permissions are verified.

Do **not** trust or import a CA that was generated before the protected execution and secret directory were established. Tightening permissions later cannot prove its private key was never copied. The guarded generator writes `certs/ca-provenance.json` only when it creates a new CA after the ACL precheck; the HTTPS helper requires its SHA-256 fingerprint to match the CA before considering trust. The receipt prevents accidental use of an older CA, but is not a substitute for protecting the code and certificate directory. Existing certificate and credential files are not replaced automatically. After the protected boundary exists, decide which existing secrets were actually configured or used and deliberately rotate those that may have been exposed; create and review a new CA fingerprint at that point.

1. After the Windows permission prerequisite passes, run `deployment/local-https/new-local-config.ps1` from PowerShell. It creates ignored `deployment/local-https/.env.local` with a random Fernet key and refuses to replace an existing file. The file must stay on this machine and out of Git. Fill the GitHub Client ID and Client Secret locally; do not send them in chat. The full launcher supplies its local PostgreSQL DSN in the process environment, which takes precedence over the example file's DSN placeholder. `ARIADNE_GITHUB_REDIRECT_URI` is already the exact callback above. The helper rejects unresolved OAuth placeholders and a missing database address.
2. Use an existing owner-protected `deployment/local-https/certs/` directory, then run `uv run --directory backend python ../deployment/local-https/generate_cert.py` from the repository root. It creates ignored local CA, server certificate, private keys and the provenance receipt there only after the ACL check passes. It refuses to overwrite existing files; retire an older local CA deliberately after the protected boundary is ready. It does **not** install trust or modify Windows/browser settings. Keep both `.key` files private and local.
3. Review the **newly generated** CA certificate and its printed fingerprint. Only after the receipt exists and the protected setup is verified, if you choose to trust this new CA for this Windows user, explicitly run `certutil -user -addstore Root deployment\local-https\certs\local-ca.pem` from the repository root. Do not use this command with the older CA. This changes the Current User Trusted Root store. The local launcher checks the matching receipt and that this CA is present before starting. A browser must actually trust this certificate for the `Secure` and `__Host-` cookies to work without certificate warnings. Some browsers may use an additional certificate store; verify the HTTPS page in the browser you use. No trust-store change is automated by these scripts.
4. In your own GitHub account, create a new OAuth app using the [official steps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app). Enter Homepage `https://localhost:8443/` and Authorization callback `https://localhost:8443/auth/github/callback`, with wildcard matching disabled. Copy only the resulting Client ID and Client Secret into the ignored `.env.local`. Leave expiring access tokens enabled. The app is not created by this repository.
5. Start the full local application with the project's launcher after its PostgreSQL schema and frontend build prerequisites are ready. The HTTPS helper `prepare-local-https.ps1` validates the ignored config, free loopback port 8443, certificate dates and Windows Current User CA trust; it exports the cert/key paths to the launcher. It does not start HTTP or silently fall back to it. Open exactly `https://localhost:8443/` in the browser, then use GitHub login. Do not open the separate demo ports for OAuth.

The full launcher owns frontend build, PostgreSQL/Qdrant/model startup and Uvicorn. It dot-sources `prepare-local-https.ps1` before a new start, then runs Uvicorn on `127.0.0.1:8443` with the supplied cert/key and `--no-access-log` so OAuth callback query codes are not logged. For a verified existing instance, `-ExistingListener` repeats the ACL, OAuth configuration, certificate and CA trust checks while allowing the already occupied port; it does not bypass security checks. [Uvicorn documents its native TLS certificate and key flags](https://www.uvicorn.org/deployment/#running-with-https). The helper accepts only the five DB/OAuth settings in `.env.local`; local model credentials are generated by the launcher in process memory.

Without the GitHub OAuth app credentials, identity/API routes return `configuration_unavailable`; TLS health and the static frontend can still respond. A local CA verification with an explicit CA file proves the transport configuration, but it does not prove Windows/browser trust or a live GitHub login. The latter requires your manual CA trust and OAuth app registration steps above.
